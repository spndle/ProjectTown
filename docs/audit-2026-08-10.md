# ProjectTown v1.0 代码审查与修复记录

审查日期：2026-08-10  
依据：`ProjectTown-项目开发文档.md`、当前 v1 后端、Godot 客户端、测试、评测与发布配置  
原则：只修复可复现或能由明确故障窗口证明的问题；不改变 v1 的单节点、单进程 SQLite 边界，不引入生产依赖，不做无关重构。

## 结论

本轮确认并修复了七类实际问题：工具副作用恢复、用户 Decision 原子性、并发执行租约、验收与预算语义、Godot 多 Quest 隔离、发布可复现性和报告可追溯性。最终全量自动化、Godot 实际 REST/WebSocket 联调及 4,320 行正式评测产物均通过复验。

## 问题与实施方案

### 1. 工具成功与事件账本存在崩溃窗口

原行为先把 action 标记为 `committed`，再追加 `ToolCommitted`。如果进程在两步之间退出，恢复流程会把里程碑重置并生成新 attempt，可能再次执行已经生效的 `write_file`。

采用方案：

- 新增 additive migration 3，为 action 增加 `committed_event_id` 和唯一部分索引；
- 外部工具仍在数据库事务外执行；成功后使用短事务同时提交 action、追加 `ToolCommitted`、更新 Quest projection 并建立链接；
- 旧数据库中缺失链接的 committed action 在打开时做幂等修复；
- 恢复保留 `running` / `verifying` 里程碑的 attempt 与预算，使用原 idempotency key 继续验收。

未采用长事务包围外部工具，因为它会放大锁持有、故障和吞吐风险；也未只增加 consumed 布尔值，因为它不能证明账本和 projection 已一起提交。

### 2. 用户 Decision 可能留下部分账本

原行为在验证修改是否合法之前，可能已经写入 Decision、Goal Contract 或 Plan。对已完成里程碑的非法修改虽最终失败，仍会留下状态或版本变化；并发 Decision 也可能产生矛盾记录。

采用方案：新增 `apply_decision()` 单事务入口，在 `BEGIN IMMEDIATE` 内重新检查 state version、`waiting_user` 状态、审批目标和已完成里程碑不变量，再一次性写入 Decision、Contract、Plan 与事件。并发请求只能有一个胜者，失败请求返回 409 且零部分写入。

### 3. 重复启动可共享并误释放同一租约

原 lease 逻辑把“同 owner 再次 acquire”视为成功。两个相同版本的并发启动因此都可能继续，失败方又会释放成功方正在使用的 lease。

采用方案：活动 Quest lease 始终独占，即使 owner 字符串相同也拒绝第二次 acquire；并发启动确定为一个成功、一个 `QUEST_LEASE_CONFLICT` 409，失败方不再拥有可释放的租约。

### 4. 验收与预算语义不完整

确认了三个独立问题：

- `required=false` 的失败 Criterion 会错误触发重规划；
- 最终 Verifier 自身耗时不计入 `max_seconds`，可能超时后仍完成；
- 恢复 active milestone 时会重复增加 step、tool-call、message 和 attempt。

采用方案：里程碑和 Quest 成功只由 required Criterion 决定，但仍保存 optional 失败证据；最终验收前后都检查墙钟预算；只有 `pending` 的新 attempt 才增加预算与 attempt。

### 5. Godot 旧 Quest 响应可污染当前 Quest

旧异步 HTTP/WS 回调没有携带来源 Quest，切换 Quest 后，旧响应可能覆盖新状态；事件 cursor 与 evidence 计数也跨 Quest 共享。WebSocket 正常时仍持续轮询全部 events，断线重连无退避，终态仍继续更新。

采用方案：所有 Quest/event/evidence/WS 信号携带 `source_quest_id`；主界面丢弃非当前 Quest 响应；切换时重置 cursor、去重集合、evidence 和连接；WebSocket 正常时停止 REST events 轮询，断线使用 1–30 秒指数退避，终态停止 timer 与 socket，手动刷新仍执行一次 REST 请求。

### 6. 发布产物在不同平台不可字节级复现

Windows 默认换行会改变 CSV、JSON、Markdown、SVG 的 SHA-256，manifest 需要人工维护；CI 检查范围与验收命令也不完全一致。Compose bind mount 对首次以 UID 10001 启动存在宿主目录权限风险，直启文档未加载 `.env`。

采用方案：所有评测文本固定 UTF-8/LF，生成器自动写 manifest 和四个 SHA-256；正式 seed 1729 产物加入字节级再生成测试；CI 覆盖 `backend tests scripts`；Compose 使用 Docker-managed named volumes；直启命令显式使用 `--env-file .env`。

### 7. 评测报告缺少原始产物入口

`report.md` 虽有汇总表，但不能直接追溯 CSV、JSON、图表和 manifest。

采用方案：生成器写入四个相对链接，并由测试校验；正式报告和 manifest 已重新生成。

## 保留边界

- 当前环境没有 Docker CLI，因此只完成 Compose 解析与契约检查，没有声称镜像或容器已运行。
- Godot 验证是 headless 引擎和真实传输冒烟，不替代人工视觉布局检查。
- 没有真实 LLM、外部账号、网络工具或生产权限验证。
- SQLite 仍是文档声明的单节点、单进程方案；本轮没有扩展为 HA 或分布式协调。
- 当前工作区没有 Git 元数据，不能生成 Git diff 或验证 `v1.0.0` tag。

## 回滚说明

- 代码与文档：从外部备份或版本控制恢复“关键修改范围”列出的文件；当前目录本身不能提供 Git 回滚。
- SQLite migration 3 是只增加 nullable 列和索引的兼容迁移，不应通过删除列回滚。若必须完全回到旧语义，应先停服，再整体恢复迁移前数据库备份。
- 正式评测产物由生成器生成；恢复相应版本的 `evaluation.py` 后，使用 manifest 中的 profile/seed 命令重新生成，不能只手改哈希。
- Godot 与后端协议必须成组回滚，避免旧回调签名与新信号参数不匹配。
